## 📌 Контекст теми

У межах **Topic 09 — SQL DML** команда підготувала комплексний набір даних для бази даних **FitServe Fitness Center Database**.

Основний підхід полягав не в розподілі окремих операцій `INSERT`, `UPDATE` та `DELETE` між учасниками, а в **розподілі логічно пов'язаних сутностей та таблиць**.

Це дозволило кожному учаснику працювати зі своєю частиною предметної області та контролювати узгодженість зовнішніх ключів між залежними таблицями.

Для `user_info` був створений розширений набір анонімізованих користувачів із різними датами реєстрації, датами народження, телефонними номерами, адресами та іншими персональними даними.

Для `users` були створені ролі `Athlete`, `Trainer` та `Administrator`.

Також реалізовано сценарій, за якого частина тренерів одночасно є атлетами. У такому випадку один `user_info_id` використовується для двох записів у `users` із різними ролями, що дозволяє коректно використовувати обмеження:

`UNIQUE (user_info_id, role)`.

Для тренерів було сформовано різні типи контрактів:

- `individual`;
- `salaried`;
- `both`.

Для контрактів `individual` та `both` були додані відповідні записи `interest_rate`.

Також були створені спеціалізації тренерів та пов'язані з ними сертифікації.

Для `session`, `athlete_session` та `trainer_session` було підготовлено більший набір даних для демонстрації реальних сценаріїв бронювання та проведення тренувань.

Окремо були підготовлені тести поведінки зовнішніх ключів:

- `ON UPDATE CASCADE`;
- `ON DELETE CASCADE`;
- `ON DELETE SET NULL`;
- `ON DELETE RESTRICT`.

Для тестів, які реально змінюють або видаляють дані, використовувалися транзакції з `ROLLBACK`, щоб після перевірки основний набір DML-даних залишався без змін.

## 🧩 Організація DML

DML-скрипт формувався з урахуванням порядку залежностей між таблицями.

Спочатку заповнювалися базові сутності, після чого — таблиці, які містять зовнішні ключі на них.

Основні залежності:

`user_info → users → athletes / trainers`

`interest_rate → trainers → trainer_specialization → certifications`

`studios → studio_type`

`studios → session → athlete_session / trainer_session`

`athletes → athlete_achievement / body_metrics / health_restriction / nutrition`

`nutrition → protein`

`packs → pack_subscription → payment → payment_discount`

`equipment → warranty`

`packs + equipment → pack_equipment`

Такий порядок дозволив виконувати `dml.sql` послідовно без необхідності тимчасово відключати `FOREIGN KEY` constraints.

Кожна основна секція `dml.sql` містить коментарі, які пояснюють:

- яку таблицю наповнює секція;
- приблизну кількість записів;
- призначення даних;
- особливості зв'язків між таблицями.

## 🧪 Перевірка constraints

Крім звичайного наповнення таблиць, команда підготувала окремі сценарії для перевірки обмежень бази даних.

Constraint tests навмисно створюють некоректні ситуації, щоб переконатися, що PostgreSQL правильно їх відхиляє.

Перевірялися:

- `CHECK`;
- `PRIMARY KEY`;
- `UNIQUE`;
- `FOREIGN KEY`;
- `NOT NULL`;
- `ENUM`.

Наприклад, тестувалися:

- некоректний вік користувача;
- негативні або завеликі числові значення;
- дублювання унікальних полів;
- посилання на неіснуючі записи;
- неправильні значення ENUM;
- некоректні дати;
- дублювання складених `UNIQUE`-зв'язків.

Окремо були протестовані правила зовнішніх ключів:

- `ON UPDATE CASCADE`;
- `ON DELETE CASCADE`;
- `ON DELETE SET NULL`;
- `ON DELETE RESTRICT`.

### 2. Чому вибрані саме такі тестові дані

Основною метою було створити не просто мінімально необхідну кількість записів, а набір даних, який нагадує роботу реального фітнес-центру.

Тому використовувалися:

- різні категорії користувачів;
- різні типи контрактів тренерів;
- атлети з різними цілями;
- тренери з декількома спеціалізаціями;
- різні сертифікації;
- різні студії та види активностей;
- спортивне обладнання;
- тренувальні сесії з різною кількістю учасників;
- різні пакети послуг;
- промокоди та знижки;
- платежі;
- дані про здоров'я;
- харчування;
- прогрес та досягнення атлетів.

Персональні дані користувачів є **вигаданими та анонімізованими** і використовуються виключно в межах навчального проєкту.

---

### 3. Як перевіряли коректність і реалістичність DML-скриптів

Після об'єднання окремих частин команда перевіряла:

- відповідність усіх `FOREIGN KEY`;
- відсутність небажаних конфліктів `PRIMARY KEY`;
- коректність `UNIQUE` constraints;
- виконання `CHECK` constraints;
- правильність значень PostgreSQL `ENUM`;
- відповідність ID між залежними таблицями;
- правильний порядок виконання `INSERT`;
- реалістичність і логічність тестових даних.

Окремі негативні тести навмисно створюють помилки PostgreSQL, щоб підтвердити роботу constraints.

Для перевірки `CASCADE` та `SET NULL` використовувалися транзакції:

`BEGIN → test operation → SELECT → ROLLBACK`

Це дозволило перевірити поведінку зовнішніх ключів без остаточної зміни тестового набору даних.
